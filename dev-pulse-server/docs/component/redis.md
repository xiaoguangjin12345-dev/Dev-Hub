# Redis缓存应用
## 1. 时间局部性
### 1.1 核心思想
- 针对选项框、指定项目或任务详情、用户姓名等热点数据，访问时首先读取Redis缓存，缓存未命中时再查询数据库并存储缓存；TTL内再次访问可直接查询缓存。
- 从而减少数据库连接池占用与磁盘I/O，提高系统整体响应效率。

### 1.2 实现要点

  - Redis缓存的Key设计与TTL设计遵循**业务需求**与**预估频率**进行。
  - **枚举、类别类选项框数据**，均可设计较长时间的TTL (一般大于6 h)，但是不能完全相同，而是范围内随机数波动，防止缓存失效时大量不同类别的请求发送至数据库
  - **项目、任务选项框数据**，由于权限控制与数据隔离，不同角色可访问的数据不同，针对Key的设计，需要添加**角色** (**或者加上用户ID**)等元素，同时此类数据的基准TTL也应根据角色调整。


## 2. 异步轮询结果
### 2.1 核心思想
  - 一个需要将结果反馈给用户的异步实现的功能，通常可将其拆分成**请求**与**查询响应**两个接口。
  - 查询响应接口由前端**限时轮询**执行；查询响应接口对请求结果的直接判断依据，就是**Redis暂存的数据**。

### 2.2 实现要点
  - **请求接口**的实现，一般需要根据业务属性设计Key，并根据Key将该请求的**Pending状态**存至Redis，并将该Key返回给前端；前端后续执行限时轮询时需要将Key作为参数传入。
  - 真正**处理业务数据的方法**，需要根据执行情况，按照此前生成的Key将**成功**或**失败**状态写入Redis，并设置TTL
  - 一般失败态的TTL较短，60 s以内；成功态的TTL没有固定约束，根据业务定即可。
  - 若为成功态，可能还需要根据业务属性存入**数据、文件相对地址或时间**等字段。
