# Redisson分布式锁应用
## 1. 任务双向选择匹配
  - 一个任务的最终只能匹配至一名开发人员，任务尝试匹配时的数据库写入过程即为临界区 (暨事务控制区)。
  - 该过程使用锁来约束，防止同一时刻不同的匹配请求同时进入临界区，在并发状态下造成**匹配数据不一致**的可能；临界区内设计**二次校验**，防止极端并发下数据前后任务匹配状态不同的可能。
  - 以上过程实现的伪代码如下：
  ```
  锁对象=任务ID;
  try{
    尝试获取锁(超时时间=0秒);
    if(获取失败){
        抛出(任务已被其他用户尝试分配)异常;
    }
    @事务控制区(回滚规则=运行时异常)
    {
        if(关联的任务状态 != 待分配){
            抛出(任务分配失败)异常;          // 防止极端并发，临界区内做二次校验
        }
        将本条申请状态设为(已同意);
        将关联该任务的其他申请记录设为(已失效);
        任务实体更新(开发人员, 匹配时间)等信息;
    }
  }catch(异常){
    抛出(任务分配失败)异常;
  }finally{
    if(当前线程持有锁){
        释放锁;                            // 无论结果如何，最终都要把锁释放
    }
  }
  ```

  
## 2. PMO相关操作
  
- 涉及**项目立项审批**、**项目结项审批**、**提交绩效评价主观部分**等操作。这些操作，任何PMO均可，没有强制指定，只需系统记录某项操作的PMO以便后续追溯即可。
  
- 这些操作若没有锁的约束，两个PMO同时进入临界区，在极端并发下，一个PMO会收到操作成功的响应信息，但其操作结果可能**已被后一个PMO覆盖**。下面是项目立项场景下的分析：
```
if(项目状态 != 待立项)
    抛出(该项目不处于待立项状态)异常;
插入项目审批记录;
if(审批结果 == 通过)
    修改项目状态(进行中);
else
    修改项目状态(待修改);
// 操作成功
```

| 时刻 | 线程1 (PMO1) | 线程2 (PMO2) |
| :---: | :---: | :---: |
| T1 | `if(项目状态 != 待立项)` | - |
| T2 | - | `if(项目状态 != 待立项)` |
| T3 | `插入项目审批记录;` | - |
| T4 | - | `插入项目审批记录;` |
| T5 | `修改项目状态(进行中);` | - |
| T6 | - | `修改项目状态(待修改);` |

> 最终两个PMO均获得操作成功的反馈，但是由于并发，最终的结果是错误的。
- 使用锁约束其中某项操作的临界区 (暨事务控制区)，可防止并发状态下两个PMO同时操作同一项记录，导致**数据覆盖**与**响应传达滞后**。过程实现可参考任务双向选择匹配的伪代码，实现方式相似。




### *Tips*
- *Redisson只是锁的实现形式之一，单体架构下使用Java原生锁也能实现以上目标。*
- *部分临界区 (比如只涉及单句SQL，或只执行一个mapper接口的)，仅使用**乐观锁**在数据库执行语句内校验，同样可行。*
- *Redis与Redisson在同项目共存，需要注意**循环依赖**问题，该问题可通过编写Redisson配置类解决。*
